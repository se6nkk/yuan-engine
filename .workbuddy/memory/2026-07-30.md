## 来源校验：卡「正在校验」根因 + 实时进度
- **根因**：`renderResult` 是生成/缓存/Obsidian/重新生成多条路径的公共入口，但 `verifySources` 只在生成分支（renderResult 之后）调用；缓存/Obsidian 路径 `readerState.sources` 永远为空 → 面板永久显示「正在校验来源...」。且原校验 4 渠道串行 `await` 无中间反馈，最差 20s+ 黑盒。
- **修复**：把 `verifySources` 触发移入 `renderResult` 末尾（覆盖所有入口），删除生成分支的重复调用；`verifySources(concept, onProgress)` 新增进度回调，每完成一个渠道调用 `onProgress(sources)`，实时 `renderSourcePanel()`。
- 4 渠道（Wikidata / SearXNG / 中文维基 / DuckDuckGo）拆成独立函数 `verifyWikidata/verifySearXNG/verifyZhWiki/verifyDDG`，各带 `SOURCE_TIMEOUT=5000` 超时；`sources` 每项带 `status: checking|hit|miss`，先 push checking 再 await 再更新，保证顺序与进度可见。
- UI：面板标题显示 `校验中 k/n` 或 `✅ 已验证` / `⚠️ 未找到可靠来源`；每个渠道行显示旋转 spinner（`.src-spinner` CSS 动画）+「校验中…」/ ✅链接 / ⬜「（未命中）」。
- 入口数据流：readerState 初 `sources:[]` → 生成/缓存都重新跑校验（缓存数据不含 sources 字段，不持久化校验结果，需每次重验）。

## 生成↔核对并行管道（恢复"逐层渐进显示"，且更早）
- 用户反馈：此前为保证"绝不展示未核对内容"改为「五层全部生成完 → 整体跑一次 L2 核对 → 才渲染」，体验退化为等全部完成。希望恢复并行：生成第 N 层时后台核对该层，同时生成第 N+1 层；首层生成+核对完即开阅读器，逐层揭示（保留 1 层缓冲，避免向前翻页撞加载墙）。
- 实现：保留**单次流式生成**（不拆成 5 次 LLM 调用），在 `callLLMStream` 的 onChunk 中按 `## 第X层` 头定界——某层出现下一层头即定界该层，立刻 `finalizeGeneratedLayer` 后台并行跑 `verifyLayerParallel`（= `factCheckAndPatch` 单层版，maxFacts=2、并发 2），生成流继续。
- 揭示调度 `scheduleReveal`：首层 genDone&&verDone → `openReaderForPipe` 开阅读器并显示第 1 层；之后每层 i 在其 genDone&&verDone 且下一层已生成（缓冲）时 `appendLayerPageToReader` 揭示；末层待 streamDone。对应用户描述：生成第2层时校验第2层、同时生成第3层；第3层生成完+第2层校验完→显示第1层，继续生成4/5。
- 阅读器内新增细进度条 `#readerGenBar/#readerGenFill/#readerGenText`（生成+核对合并：生成占55%、核对占45%，缓动定时器 `startPipelineProgress` 在首页条与阅读器条间平滑交接）；点状导航映射每层状态 `.gen`(生成中)/`.ver`(核对中,脉冲)/`.ready`(已核对待揭示缓冲)/`.active`+`.done`(已读)。`updateReaderNav` 末层未就绪显示禁用的「生成中…」，全部就绪才显示「导出」。
- 抽离 `readerShellHTML/attachReaderShell/startSourceVerify/hideHomeProgress` 供完整渲染（缓存/Obsidian/子词条/重新生成）与管道共用；`renderResult` 仍走整篇 L2 核对（完整就绪后隐藏细进度条）。`closeReader` 清空 `pipeline` 防陈旧状态。
- 最终回写：流结束后 `pipe.verifiedMd.join('\n---\n')` 拼成整篇已核对内容，`dbPut`+`syncToObsidian`（`_verified:true`）。
- 验证：`node --check` 零错误。

## BUG 修复：生成完进不去阅读器（卡在首页）
- 现象：生成完成后阅读器始终不打开，人停在首页。
- 根因：`finalizeGeneratedLayer` 里 `verifyLayerParallel`（`factCheckAndPatch`→`callLLMJson`/`factSearch` 均为网络调用）**无超时兜底**。某层核对挂死则 `verDone[k]` 永不置位 → 第0层永远不满足「生成+核对完」开门条件；同时 `await Promise.all(pipe.verPromises)` 永不返回，连流结束后 `if(!pipe.readerOpen) openReaderForPipe` 兜底都跑不到。同类于此前来源校验 CORS 挂死的坑——**任何网络调用必须带超时**。
- 修复：① 给每层核对加 `Promise.race` 超时 `VERIFY_LAYER_TIMEOUT=12000ms`，超时/失败回退原内容（`md=raw`），保证 `verDone[k]` 一定置位；② verify 的 IIFE 整体 try/catch，且 `scheduleReveal` 调用也兜底，使 `verPromises` 中**每个 promise 永不 reject**（否则 `Promise.all` 被单个 reject 打断、阻断强制开门）；③ 流结束处强制开门再套一层 try/catch。
- 效果：最坏情况下第0层核对 12s 内必以原内容兜底开门；管道不再卡死。
- 验证：`node --check` 零错误。

## 揭示策略调整：开门闸门改为「前两页就绪」+ 去 buffer
- 用户反馈：进阅读器后第1页内容少、很快读完，但「继续」按钮不能点（要等第2页），体验差。希望**在首页等到前两页都生成+核对完再进入**，进去就有两页可读，后三页后台继续。
- `scheduleReveal` 开门闸门：`genDone[0]&&verDone[0] && (totalLayers<2 ? true : genDone[1]&&verDone[1])` —— 前两层都就绪才开；揭示循环**去掉 buffer**（原 `buffer = streamDone || genDone[i+1]` 要求下一层先生成才显示当前层，导致前沿页被卡），改为「所有已就绪层立即揭示」（`while(genDone[i]&&verDone[i])`）。
- `openReaderForPipe`：`revealedUpTo` 初始化 `-1`，交 `scheduleReveal` 从 0 揭示；进去即可见第1、2页，「继续」立即可点（→第2页已就绪）。`updateReaderNav` 原有逻辑（`cur<revealed` 显示可点继续；`cur===revealed&&<末层` 显示禁用「生成中…」）无需改，与新语义一致。
- 效果：首页多等约一层（第2页）生成+核对，但进入后立即可读两页、继续顺畅；后三页在后台生成，用户读完前两页时通常已就绪。
- 验证：`node --check` 零错误。
